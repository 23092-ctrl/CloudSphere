(?) Question de réflexion : Pourquoi ne pas mettre 8 Go de RAM ? Pensez à la sur-allocation.
Réponse : Dans un hyperviseur de Type 2 (hébergé sur un OS client physique), allouer 8 Go à une seule VM risque de provoquer une sur-allocation (overcommitting) néfaste : 1. L'OS hôte physique n'a plus assez de RAM disponible pour ses propres processus. 2. L'hyperviseur est contraint d'utiliser le fichier d'échange (swap sur disque), entraînant une chute drastique des performances I/O. 3. Pour un serveur Linux sans GUI exécutant quelques conteneurs, 2048 Mo (2 Go) est le dimensionnement optimal respectant le principe de juste allocation des ressources Cloud.

(?) Question de réflexion : Quelle est la différence entre un Snapshot et une Sauvegarde (Backup) complète ?
Réponse :
  • Snapshot (Instantané) : Fige le disque à l'instant T en créant un fichier différentiel (delta file). L'hyperviseur redirige les nouvelles écritures vers ce delta. Le snapshot dépend obligatoirement du disque parent : si le disque virtuel original est corrompu ou déplacé, le snapshot devient totalement inutilisable.
  • Sauvegarde (Backup) : Copie intégrale, autonome et décorrélée de tous les blocs de données de la VM, idéalement stockée sur un support physique ou Cloud distant. Elle peut être restaurée même après destruction complète de l'hyperviseur d'origine.

Partie 3 : Laboratoire Réseau (NAT, Bridged, Host-Only)

Mode Réseau Sortie Internet (VM ➔ Extérieur) Accès depuis le PC Hôte (Hôte ➔ VM) Visibilité sur le Réseau Local (LAN) Cas d'Usage Typique
NAT (Défaut) OUI (via routeur hôte) NON (bloqué sans port forwarding) Invisible (masquée derrière l'IP hôte) Mises à jour système, téléchargements.
Bridged (Pont) OUI (IP sur le réseau box/wifi) OUI (ping direct sur même subnet) EXPOSÉE (vue comme machine physique) Serveurs publics devant être joints par le LAN.
Host-Only (Privé) NON (aucun routage externe) OUI (communication bidirectionnelle) Totalement isolée du monde extérieur Bacs à sable (sandbox malwares, tests isolés).

cheikh@23092-vm-base:~$ docker run -d -p 8080:80 --name mon-serveur nginx c1a98e6f3b0e12d4a78c94e0192a8e7d23a1098b67f12e847c2901928374a56b cheikh@23092-vm-base:~$ curl -I http://localhost:8080 HTTP/1.1 200 OK Server: nginx/1.25.4
(?) Question de réflexion : Cohabitation Apache (80) et Nginx (8080). Pourquoi peuvent-ils fonctionner ensemble ? Que se passerait-il avec -p 80:80 ?
Réponse : 1. Pourquoi cela fonctionne : Apache est lié directement au port 80 de la pile réseau de l'hôte VM (Host Network Namespace). Nginx s'exécute dans un Network Namespace complètement isolé à l'intérieur du conteneur où il écoute sur son propre port 80 interne. Docker utilise iptables (DNAT) pour rediriger le port 8080 de la VM vers le port 80 du conteneur. Comme les deux processus n'écoutent pas sur le même port de la VM hôte, il n'y a aucun conflit.
2. Avec -p 80:80 : Docker tenterait de réserver le port 80 de la VM hôte. Le système renverrait une erreur immédiate : Error response from daemon: driver failed programming external connectivity: bind: address already in use, car Apache écoute déjà sur ce port.
(?) Question de réflexion : Si vous supprimez le conteneur (docker rm -f mon-serveur) et le relancez, la modification HTML est-elle conservée ? Pourquoi ? Comparez avec un snapshot VM.
Réponse : La modification est perdue. Par conception, les conteneurs sont éphémères et sans état (Stateless). Toute écriture effectuée sans volume persistant est stockée dans la couche superficielle d'écriture (Container Writable Layer). Lors de la suppression du conteneur, cette couche est définitivement détruite. À l'inverse, un snapshot de VM fige l'état de l'intégralité du disque virtuel au niveau bloc et permet de restaurer exactement les données modifiées.

(?) Question de réflexion : Comparez la taille de l'image (docker images) à celle du disque de votre VM. Que concluez-vous ?
Réponse : L'image mon-site-perso basée sur Alpine Linux pèse seulement ~23.5 Mo. En comparaison, le disque virtuel de la VM Ubuntu Server pèse environ 4.5 Go (4500 Mo). Conclusion : L'image conteneurisée est près de 200 fois plus légère que la machine virtuelle. Le conteneur ne contient que l'application et ses dépendances strictes en partageant le noyau Linux de l'hôte, tandis que la VM embarque un noyau complet, les modules matériels, les démons systemd et tous les utilitaires OS.
